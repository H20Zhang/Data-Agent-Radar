# Business Truth, not SQL Accuracy: From Executable Queries to Semantic Correctness

[中文](2608.09254.md) | **English** · [Home](../README.en.md) · [Research Library](../library/README.en.md)

[Paper](https://arxiv.org/abs/2608.09254) · **Importance: 4/5**

> **Research delta.** Analytics-agent correctness should include whether the business question is well defined, whether the warehouse can answer it, whether deterministic checks accept the result, and when the agent should clarify or abstain—not merely whether generated SQL executes.

## Problem

The dangerous enterprise failure is often **false success**: a syntactically valid query returns a number under the wrong business definition, an ambiguous metric is silently chosen, the schema has drifted, or the source cannot actually support the requested answer.

Direct NL→SQL evaluation tends to collapse these failures into execution success.

## Mechanism

The system inserts rule/metadata/semantic gates around execution:

`question → ambiguity/answerability check → semantic/schema grounding → SQL/tool execution → deterministic post-execution checks → answer | clarify | abstain`

The design makes “do not answer yet” a valid system outcome.

## Closest comparison

The headline comparison includes a larger direct-prompted model, but model size and scaffolding change together. The evidence therefore supports the **rule-gated semantic/verification package** more strongly than a claim that the smaller model itself is superior.

## Decisive evidence

The important evaluation shift is the use of business-truth, clarification/abstention, and false-success targets in addition to SQL accuracy. That changes the success contract even before attributing gains to a particular component.

## What remains unproven

Component attribution remains weak: semantic rules, answerability gating, and post-execution checks are not isolated cleanly. The semantic layer can itself be stale or wrong, raising a second systems problem—who maintains business definitions and how is drift detected?

## Field-map consequence

For Data Agents:

`execution success ≠ semantic correctness ≠ safe-to-answer`

Verification, clarification, and abstention belong inside the agent correctness contract rather than as product-side guardrails.
