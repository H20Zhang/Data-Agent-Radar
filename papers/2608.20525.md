# Bolo：把模型仓库修复推进到运行与静态数据流检查

**中文** | [English](2608.20525.en.md) · [返回首页](../README.md) · [Research Library](../library/README.md)

[Paper](https://arxiv.org/abs/2608.20525) · **Importance: 3/5**

> **Research delta.** Bolo 在 fresh environment 中修依赖、补丁或生成 inference template，运行默认输入，再用 HalluVer 检查代码是否真的加载目标模型、消费任务输入并把结果传到输出；它把“能启动”与最小 artifact dataflow 分开。

## Problem

模型仓库常只有 weights，缺少可运行 pipeline，或者样例代码虽然执行却绕过目标模型、忽略输入并返回无关输出。下游 AI database 不能把一次无报错运行当成可用服务。

## Mechanism

Bolo 将仓库分为官方 pipeline 失败、缺少/不支持 pipeline tag、非 Transformers 三类。它先在新 venv 修复依赖，再 patch 或用模板生成代码与 `requirements.txt`，运行默认输入，最后用 AST/data-flow checker HalluVer 检查目标模型、任务输入与最终输出的连接。失败会在 50 个 tool calls 或每模型 20 分钟上限内继续修复/重生成。

## Closest comparison

Type II/III 与 mini-swe 使用同一 ChatGPT-5.1-Codex-mini backend、50-call budget 与 sandbox，但 Bolo 具有 task-specific tools 和更长 prompt，mini-swe 使用 unrestricted bash。因此比较支持专门化 package，不隔离 prompt 或 tool interface。

## Decisive evidence

- Type I 的平均 runnable coverage 从官方 baseline 的 **69.3%** 上升到人工准备依赖后的 88%，Agent patch 后 96.1%，fallback generation 后 97.3%。主要第一段增益来自人工 dependency curation。
- Type II：Bolo 97.27% runnable，mini-swe 93.05%，API cost 37.26 vs 36.65 美元。Type III：86.08% vs 73.12%，但成本 134.54 vs 53.60 美元，约高 2.5 倍。
- HalluVer 在 481 个 runnable Type I 中标记 91 个可疑程序，在 1,316 个 Type II 中标记 119 个。人工 audit 的 recall 为 98.5% / 100%，precision 只有 79.8% / 78.9%，会误拦大量有效程序。
- HalluVer 过滤后，Type I coverage 降到 95.3–95.6%，Type II 降到 88.5%。

## Cost and failure boundary

样本排除超过 16GB、需要外部服务协议、低下载量与部分 vLLM 模型，不能代表完整长尾。只使用一个 LLM 与 A40 环境，没有 prompt、hardware、dependency drift 或 repeated-run robustness。

人工准备 task dependencies、offline API collection 与错误分析把劳动移出 Agent 比较。论文没有 GPU 成本、总 wall time、token、安装失败分布或供应链安全评价。

最重要的是，HalluVer 只检查“加载模型 → 消费输入 → 输出路径”的静态结构，不验证预测属于正确 fine-grained task 或语义正确。Type III 甚至不在 HalluVer 的 Transformers API collection 覆盖内；论文明确把 task-specific output verification 留给未来工作。

## Claim ceiling

在一个经过筛选的模型仓库样本上，task-specific repair package 比 mini-swe 生成了更多 runnable pipelines，静态 dataflow screen 也删除了不少可疑程序。它交付的是 runnable + structure-checked template，不是 behaviorally verified model service。

## Field-map consequence

该工作作为 `early_signal` 进入 **Verification & Recovery**，连接 Execution & Transformation 与交付。它把 runtime success 和最小 artifact dataflow 分开，但没有通过语义/业务真实性门槛，稳定地图不变。
