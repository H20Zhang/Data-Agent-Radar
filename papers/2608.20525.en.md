# Bolo: Move Model-Repository Repair to Runtime and Static Dataflow Checks

[中文](2608.20525.md) | **English** · [Home](../README.en.md) · [Research Library](../library/README.en.md)

[Paper](https://arxiv.org/abs/2608.20525) · **Importance: 3/5**

> **Research delta.** Bolo repairs dependencies, patches or generates an inference template in a fresh environment, runs a default input, and then uses HalluVer to check that code loads the target model, consumes task input, and carries the result to output. It separates startup success from minimal artifact dataflow.

## Problem

Model repositories may contain weights without a runnable pipeline, or examples that execute while bypassing the target model, ignoring input, or returning unrelated output. A downstream AI database cannot treat one error-free run as a usable service.

## Mechanism

Bolo classifies repositories into failed official pipelines, missing/unsupported pipeline tags, and non-Transformers implementations. It repairs dependencies in a new venv, patches or template-generates code and `requirements.txt`, runs a default input, and then applies the AST/data-flow checker HalluVer to the target model, task input, and final output. Failures trigger repair or regeneration within 50 tool calls and 20 minutes per model.

## Closest comparison

For Type II/III, mini-swe shares the ChatGPT-5.1-Codex-mini backend, 50-call budget, and sandbox. Bolo has task-specific tools and a longer prompt, while mini-swe has unrestricted bash. The comparison supports the specialized package, not an isolated prompt or tool-interface effect.

## Decisive evidence

- Type I average runnable coverage rises from **69.3%** for the official baseline to 88% after manually prepared dependencies, 96.1% after agent patching, and 97.3% after fallback generation. The largest first gain comes from human dependency curation.
- Type II: Bolo reaches 97.27% runnable versus 93.05% for mini-swe, at $37.26 versus $36.65 API cost. Type III: 86.08% versus 73.12%, but at $134.54 versus $53.60—about 2.5× the cost.
- HalluVer flags 91 of 481 runnable Type I programs and 119 of 1,316 Type II programs. Human audit estimates 98.5% / 100% recall but only 79.8% / 78.9% precision, so many valid programs are blocked.
- After HalluVer filtering, Type I coverage falls to 95.3–95.6% and Type II to 88.5%.

## Cost and failure boundary

The sample excludes repositories above 16GB, external-service agreements, low downloads, and some vLLM models, so it does not represent the full long tail. One LLM and one A40 environment are used, without prompt, hardware, dependency-drift, or repeated-run robustness.

Manually prepared task dependencies, an offline API collection, and error analysis move labor outside the agent comparison. GPU cost, total wall time, tokens, installation-failure distributions, and supply-chain safety are absent.

Most importantly, HalluVer checks the static structure “load model → consume input → output path.” It does not verify the intended fine-grained task or semantic correctness. Type III is outside its Transformers API collection, and the paper explicitly leaves task-specific output verification to future work.

## Claim ceiling

On a selected repository sample, a task-specific repair package produces more runnable pipelines than mini-swe, and a static dataflow screen removes many suspicious programs. The deliverable is a runnable, structure-checked template—not a behaviorally verified model service.

## Field-map consequence

This is an `early_signal` in **Verification & Recovery**, connected to Execution & Transformation and delivery. It separates runtime success from minimal artifact dataflow but does not clear semantic or business-truth verification; the stable map stays unchanged.
