# AgentSM：把历史 Text-to-SQL Execution 变成可复用 Semantic Memory

**中文** | [English](2601.15709.en.md) · [返回首页](../README.md) · [Research Library](../library/README.md)

[Paper](https://arxiv.org/abs/2601.15709) · **Importance: 4/5**

> **Research delta.** AgentSM 不只把过去 SQL/example 存进 retrieval store，而是把成功 execution trace 整理成更可解释的 **semantic program / reusable reasoning pattern**，让后续 query 复用 database-specific knowledge。

## Problem

Enterprise Text-to-SQL 反复面对同一个 database，却经常把每个新 query 当 cold start。历史上已经探索过的 join path、business concept、filter pattern 与 execution correction 没有被系统性复用。

直接存 raw trajectory 又很长、噪声多，而且含有 query-specific binding，不一定适合新任务。

## Mechanism

`successful execution trace → extract/normalize semantic program → persistent semantic memory → retrieve relevant prior program → adapt to current query → execute/verify`

它试图把“过去怎么解过”变成比 raw SQL 或自然语言 summary 更结构化的 reusable state。

## Closest comparison

真正应比较的是：

`no memory`、`raw demonstration retrieval`、`trajectory summary`、`semantic-program memory`

在相同 database、retrieval budget 与 actor context 下分别有什么收益。

如果 semantic program 的生成过程额外用了更强 model 或人工 curation，必须单独计入。

## Decisive evidence

这项工作最重要的研究信号是 **database-specific experience 可以被持久化成可复用 execution knowledge**，而不只是把每个 SQL 当作独立 few-shot example。

它把 Text-to-SQL agent 从 per-query reasoning 往 longitudinal system 推了一步。

## What remains unproven

最大风险是 drift：schema、business logic、data distribution 或 tool behavior 改变后，旧 semantic program 可能从 useful experience 变成 stale prior。

还需要处理冲突/版本、memory utility attribution，以及什么时候应该更新/删除旧 program。否则 persistent memory 只是把 historical bias 固化下来。

## Field-map consequence

Data Agent 的 Learning & Reuse 不应只等同于 fine-tuning。一个独立方向是：

`execution experience → persistent interpretable memory → future workflow reuse`

它和 Agent Memory Radar 的 procedural memory 问题有直接交叉，但这里的 workload-specific constraint 是 database/schema/tool drift。
