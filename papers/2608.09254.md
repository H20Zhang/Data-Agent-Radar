# Business Truth, not SQL Accuracy：从“能执行”到“业务语义正确”

**中文** | [English](2608.09254.en.md) · [返回首页](../README.md) · [Research Library](../library/README.md)

[Paper](https://arxiv.org/abs/2608.09254) · **Importance: 4/5**

> **Research delta.** 这项工作把 analytics-agent correctness 从“SQL 能执行 / execution match”往前推进了一步：**系统必须知道业务定义是否明确、warehouse 是否真的能回答、结果是否通过 deterministic checks，以及什么时候应该 clarification / abstain。**

## Problem

Enterprise analytics 中最危险的 failure 往往不是 syntax error，而是 **false success**：query 正常执行、返回一个数字，但业务定义错了；用户的问题存在多个合理口径；schema 已 drift；或者 source 根本不足以回答。

Direct NL→SQL 很容易把“生成一个合法 query”当作任务完成，而 production user 真正在意的是 business truth。

## Mechanism

论文中的系统使用规则/metadata/semantic information 在执行前后加 gate：

`user question → ambiguity/answerability check → semantic/schema grounding → SQL/tool execution → deterministic post-execution checks → answer | clarify | abstain`

关键变化不是单纯多一个 verifier，而是**把不能安全回答也视为一类合法 outcome**。

## Closest comparison

Headline 比较包括一个 direct-prompted 更大模型 baseline。但这个比较同时改变了 model size 与 scaffolding，因此不能把结果解释成“小模型本身更强”。

当前证据更支持：**rule-gated semantic/verification package 比 direct prompting 更可靠**。

## Decisive evidence

论文的核心 evaluation 不再只看 SQL accuracy，而强调 Business Truth Rate、clarification/abstention 和 false-success 类错误。这个 metric shift 本身比某个单一 leaderboard 数字更重要，因为它改变了 success contract。

## What remains unproven

最关键的 attribution 缺口是缺少严格 component ablation：semantic rules、answerability gate、post-execution checks 各自贡献多少并不完全清楚。

另一个更难的问题是 semantic layer / business rule 本身也可能过时或错误。未来系统必须说明谁维护这些规则、如何检测 drift、当 rule 与 raw data 冲突时信谁。

## Field-map consequence

Data Agent 的 verification stage 应独立存在：

`execution success ≠ semantic correctness ≠ safe-to-answer`

因此 clarification、abstention、business truth 与 artifact validation 不该被当作产品层的“额外 guardrail”，而是 agent correctness 的一部分。
