# VAT decomposition：用否证标准检验 Agent 分工粒度

**中文** | [English](2608.23395.en.md) · [返回首页](../README.md) · [Research Library](../library/README.md)

[Paper](https://arxiv.org/abs/2608.23395) · [Code, data, and traces](https://github.com/pedro-santos-eng/Right-sizing-LLM-agent-decomposition-in-VAT-determination) · [Archived artifact](https://doi.org/10.5281/zenodo.22083282) · **Importance: 4/5**

> **Research delta.** 这项 4,400-run pilot 固定 VAT 子任务、工具、schema、验证、合并策略与基础模型，只改变五个依赖子任务如何分给一至五个 worker；它还用 token-matched sensitivity 和三类故障注入检验“更多 Agent 更好”是否只是预算或恢复机制的假象。

## Problem

多 Agent 设计常把分工数量与 prompt 预算、上下文切分、ledger、局部重试和验证一起改变。即使某个配置得分更高，也很难知道是 Agent 数量、依赖边界，还是额外计算带来的收益。本文把封闭 VAT determination 拆为分类、管辖地、税率、豁免与 reverse-charge synthesis，并尝试只扫描 worker partition。

## Mechanism

四个 orchestrated 条件 C1–C4 共享 deterministic Magentic-One-style orchestrator、task/progress ledgers、typed records、schema validation 与 dependency-order dispatch。C1 让一个 worker 完成全部五项；C2、C3 在依赖链中部放置一或两个 partition boundary；C4 每项一个 worker。S0 是无 orchestrator 的 tuned monolith，完整生成 trace 后最多整体修复三次。确定性规则引擎只产生合成 oracle 标签，不是比较系统。

官方工件包含 40 个 eval cases、8 个 dev cases、oracle、prompts、injection plan、4,400 条 canonical raw traces、评分与分析脚本；另保留 2,400 条缺陷修复前的 superseded traces。设计中的否证标准在当前仓库历史里早于结果提交，但历史曾重写，且三次 harness 缺陷在运行后修复并全量重跑，因此更准确的说法是 **repository-precommitted criteria with disclosed repairs**，不是第三方封存的 preregistration。

## Closest comparison

最接近 Agent 数量对照的是 C1–C4：同一 orchestrator 和 activity surface，仅改变五项工作如何分配。但不同 partition 仍改变上下文切分、handoff 暴露和局部恢复单位。S0 与 C1 同为单 worker，却同时改变 orchestrator、ledgers、dispatch、validation localization 与 repair state，不能隔离 orchestration 单一因果效应。

## Decisive evidence

- 主实验每个条件为 40 cases × 5 repeats。准确率点估计为 S0 **0.755**、C1 **0.720**、C2 **0.830**、C3 **0.830**、C4 **0.770**；C3 相对 S0 多约 14% tokens、慢约 42%。
- 四项预设 headline tests **没有一项通过 Holm correction**。C2–C1 的 paired CI 为 +0.110 [+0.010,+0.210]，但 Holm-adjusted p=.172；C2/C3 对 C4 的区间均跨零。因此作者按自己的标准判定 intermediate optimum **unsupported**。
- token-matched S0′ 比 C2 低 6.5 点，但区间 [−0.165,+0.025] 跨零；它既不能证明 prompt budget 解释了差异，也不能证明 partition 有独立增益。
- 一次性 tool outage 通常被所有配置吸收；timeout 条件下 C1 的 +16 点伴随约 2.9× token 总量，更像故障触发的重新采样，不能当作无成本恢复优势。
- 注入一条 schema-conforming、oracle-wrong 记录后，所有配置都明显下降：S0 到 **0.560**，C1 到 **0.405**，C2/C3 到 **0.345**，C4 到 **0.310**。这说明 schema / citation presence validation 几乎不能识别业务内容错误。

## Cost and failure boundary

主实验每 case 的平均 token-derived cost 约为 S0 $0.0181、C1 $0.0172、C2 $0.0220、C3 $0.0210、C4 $0.0238；价格固定在论文当时，不能外推为持久服务成本。Latency 是 capped concurrency 下的中位 case latency，没有 p95/p99；forced timeout 立即抛错，也不模拟真实 provider 等待或计费。

内容故障比较还存在 timing confound：S0/C1 在完整 trace 已生成后才被覆写，而有 handoff 的条件可能让下游 worker 真实消费错误记录。结果支持“handoff 中的 schema-valid semantic corruption 很危险”，但不能无混杂地证明 Agent 越多越脆弱。

## Claim ceiling

这项研究证明，一个高度可复核的合成 pilot 可以同时检验分工点估计、预算替代解释和故障传播；它还给出强负面证据：当前 validation 无法阻断符合 schema 的业务内容错误。证据不证明中间分工最优、多 Agent 优于单 Agent、matched-token 已排除预算混杂，或合成 oracle 等同真实 VAT / legal truth。

## Field-map consequence

该工作以 `early_signal` 进入 **Planning & Semantic Interaction**，并连接 Verification & Recovery。它为“按依赖层放置 partition boundary”提供可测试的候选控制面，但没有形成趋势，稳定 Field Map 不变。
