# CIPHER：把 Data-Science Test-Time Scaling 拆成 Exploration 与 Selection

**中文** | [English](2607.14386.en.md) · [返回首页](../README.md) · [Research Library](../library/README.md)

[Paper](https://arxiv.org/abs/2607.14386) · **Importance: 4/5**

> **Research delta.** CIPHER 不让整个 data-science trajectory 被第一个 hypothesis 锁死，而是先生成多个不同 initial states / plans，再把 **exploration 与 selection 解耦**，之后并行推进较有希望的路径。

## Problem

复杂 data-science task 的早期 decision 往往高影响、低证据：选什么 feature、分析方向、model family 或数据处理路线，都可能在真正执行几步之后才知道好坏。

Single-trajectory agent 一旦第一步选错，后续大量 tool/code execution 都会沿错误方向继续投入。

## Mechanism

核心控制流可以理解为：

`task → generate diverse candidate initial states → evaluate/select candidates → execute multiple trajectories → compare results → return best artifact`

它把 test-time compute 用在**扩大 hypothesis coverage**，而不是只在一条 trajectory 上继续加 reasoning token。

## Closest comparison

真正应该比较的是：同一 base model / tool environment / total compute 下，`one trajectory with more budget` vs `multiple diverse starts + selection`。

如果只是给 CIPHER 更多 parallel branches，而 baseline 仍是单路径固定 budget，那么 gain 同时混入了额外 test-time compute。

## Decisive evidence

论文的主要价值在于说明：data-science agent 的 test-time scaling 可以发生在 **plan/state diversity**，而不是只有 sampling more final answers。对这类任务，early exploration quality 会决定之后大量 execution cost 是否浪费。

## What remains unproven

最关键问题是 total-cost matching：候选 plan generation、selection、parallel execution 都会增加 tool/compute budget。需要看相同美元/latency 下，多样化搜索是否仍优于更强单 trajectory controller。

另一个问题是 selection reliability：如果 early proxy 和最终 artifact quality 相关性弱，系统可能只是更快地挑错方向。

## Field-map consequence

它把 Data Agent planning 从“生成一个 plan”变成：

`plan generation × diversity × selection × execution allocation`

因此 test-time scaling 本身应成为可单独研究的 control axis。
