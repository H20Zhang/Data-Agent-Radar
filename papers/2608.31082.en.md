# Agentic Data Cracking: Turn paid document reads into cross-query structured state

[中文](2608.31082.md) | **English** · [Home](../README.en.md) · [Research Library](../library/README.en.md)

[Paper](https://arxiv.org/abs/2608.31082) · **Importance: 4/5**

> **Research delta.** The important move is not merely adding another extraction agent. It turns document prefill already paid for by one query into shared, persistent structure that later, different queries can reuse. Agentic Data Cracking forks a bounded cracking branch only after the answer agent has opened a document because of a real miss, extracts evidence-backed entities / attributes / relations, and lets later queries read those structures before falling back to raw text. For Data Agent Learning & Reuse, this exposes a new control boundary: **the reusable object can be a workload-materialized data substrate rather than an answer or trajectory.**

## Problem

Multi-step data reasoning is often prefill-heavy rather than decode-heavy. An agent needs a few scattered facts but repeatedly reloads whole web pages, reports, or PDFs; related queries can therefore pay the same document-reading cost again and again.

The two obvious extremes are unattractive. Structuring the whole corpus upfront spends unbounded extraction effort on entities and relations that may never be queried. Extracting only the current query's needed facts avoids upfront work but throws away cross-query locality. The paper asks: **can the observed workload decide when and what to structure, so a read that already happened becomes a shared asset?**

## Mechanism

Agentic Data Cracking places the write boundary after a real document miss. The main reasoning agent first queries a catalog of existing cracked objects. On a hit, it reads compact structured values plus evidence without opening the raw document; on a miss, it follows the normal path and opens the document.

Once the document is in context, the system forks a cracking sub-agent from the same loaded prefix. Rather than caching only the requested fact, this branch uses a fixed **4K output-token budget** to speculate about nearby entities, attributes, and relations that future related queries may need. It emits schema-constrained JSON; normalization, grounding, and invariant checks run before insertion into the shared store. Every cracked object retains its source/evidence region, and list-valued relations are reusable only when extracted completely. Raw-document fallback remains available, so the structured layer is not the sole correctness path.

## Closest comparison

The paper's strongest matched control is the original FanOutQA agent. Both conditions use Claude-Haiku-4.5, the same FanOutQA instructions / prompts / filesystem tools, and prompt caching. The primary change is the cracking instructions plus structured read/write interface. This is a useful system-level comparison for asking whether persistent structured reuse lowers end-to-end token and API cost.

It does not isolate the narrower mechanism claim. The missing closest simple control is a **demand-only persistent cache**: store only facts actually requested by the current miss, with the same extra decode and storage budget, and perform no speculative nearby extraction. Without that arm, the 53% headline cannot be credited specifically to speculation; some or most of the gain may come from persistence and avoiding document reopens.

## Decisive evidence

- FanOutQA itself has little cross-query document reuse, so the authors generate one related-but-different preceding question for every original test question and have a human verify it. Primary metrics are still reported only on the original test questions.
- Under that workload, mean prefill falls from **189K to 87K tokens** and mean API cost from **$0.26 to $0.12**, the roughly **53% headline cost reduction**. LLM-judged accuracy is 42% versus 43% for baseline (p=.39, not significant), while word-match accuracy drops 2 points.
- The fixed 4K-token cracking budget produces roughly 150 cracked objects and is included in cost. The paper reports about **12% per-question overhead** for cracking decode plus cache reads. Gains are heterogeneous: at the 90th percentile of paired cost ratios, cracking costs **1.24× the baseline**, exposing the no-reuse failure case.
- In the stronger-locality Hitchcock case study, 20 warm-up related questions precede 10 test questions and mean cost drops from $0.81 to $0.27. This is better interpreted as a longer-running workload opportunity than as independent generalization evidence.

The strongest conclusion is system-level: when a workload repeatedly reaches the same documents for different attributes, persistent partial structure can trade bounded extra decode now for fewer raw-document prefills later.

## Cost and maintenance boundary

A strength of the paper is that online token and API costs are central rather than hidden: prompt-cache reads, cracking decode, and negative savings on no-reuse questions are all visible.

The long-run maintenance ledger is still incomplete. The current implementation assumes a **static corpus**. The discussion suggests dropping or refining cracked objects after edits, but does not measure stale-fact detection, revision binding, conflict resolution, global store growth, catalog overhead, or reverification cost. Enterprise documents change permissions, versions, numbers, and business definitions, so a claim that the accumulated structure becomes increasingly valuable must also price invalidation and governance.

## Skeptical audit

First, **locality is deliberately constructed as an experimental treatment**. Original FanOutQA rarely reopens the same documents, so each test question receives a specially generated related predecessor and is evaluated against a warmed store. This cleanly asks whether the mechanism works when locality exists, but it does not estimate the frequency, distribution, or break-even point of locality in real enterprise workloads.

Second, the matched baseline isolates the complete cracking interface, not the speculative policy. Shared storage, catalog lookup, structured reads/writes, grounding checks, and speculative extraction change together. A same-budget demand-only fact cache / non-speculative extraction control is absent, so system savings cannot be assigned specifically to agent-discovered semantic speculation.

Third, accuracy preservation depends heavily on conservative raw-document fallback. That is good engineering, but it means cost gains jointly depend on miss policy, catalog resolution, prompt caching, and workload order. For enterprise data, the next test should measure whether stale or wrong structured state changes later behavior, not only whether average final-answer quality stays similar on the current benchmark.

## Claim ceiling

The evidence supports: **under the paper's constructed related-query locality, a Data Agent can turn already-opened documents into shared evidence-backed structure, substantially reducing later prefill/API cost after accounting for cracking overhead while preserving approximate answer quality through raw fallback.**

The evidence does not establish that speculative cracking beats a same-budget demand-only persistent cache, that 53% savings transfer to real workloads with unknown locality, or that dynamic corpora can ignore stale-state, invalidation, permissions, and maintenance cost.

## Field-map consequence

This work enters **Learning & Reuse** as an `early_signal`, with a connection to Data Discovery & Grounding. It expands the reusable object from prior answers / workflow memory to workload-materialized shared data structure. One paper, without the closest demand-only-cache control or real locality/drift measurement, does not change the durable Field Map.
