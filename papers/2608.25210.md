# BLIP：把 provenance 变成可执行的答案复现证据

**中文** | [English](2608.25210.en.md) · [返回首页](../README.md) · [Research Library](../library/README.md)

[Paper](https://arxiv.org/abs/2608.25210) · **Importance: 4/5**

> **Research delta.** BLIP 的重要性不在于又生成一组“相关句子”，而在于把 provenance 的判据从相关性改成可执行复现：给定完整输入上的模型答案，寻找一个更小的输入子集，使同一模型在该子集上仍产生相同或等价答案。这个定义提供了比 embedding / LLM 自报来源更强的 operational witness；但它证明的是**答案可复现性**，不是答案正确性、业务真实性或完整 Agent workflow 的 provenance。

## Problem

LLM 用于文档分析、合同抽取、研究问答或其他 data processing 时，通常只给最终答案。常见 provenance 方法要么取 embedding 相似的片段，要么让模型自己解释“答案来自哪里”。这两类结果可以看起来合理，却没有一个关键保证：如果只保留这些片段，模型是否真的还能产生同一个答案？

对 Data Agent 来说，这个区别很重要。citation、retrieved context 和 verification artifact 经常被混成“证据”，但它们支持的 claim 不同。BLIP 试图建立一个更窄但可测试的边界：**这组输入是否足以重现当前模型的当前答案？**

## Mechanism

论文定义 verifiable provenance 为完整输入文本的一个子序列 `P`：把 `P` 单独交给同一 LLM 后，输出必须与完整输入上的答案相同或语义等价。若删除 `P` 中任意一句都会使答案改变，则它还是 minimal verifiable provenance。

穷举所有输入子集不可行。BLIP 因此设计八种搜索策略，并提供 adaptive strategy 根据当前查询/文档行为选择搜索方式；论文还扩展到寻找多个 minimal provenances。关键系统思想是把 LLM 当作昂贵的 membership/equivalence oracle，在保证最终 witness 可复现答案的前提下减少额外调用。

## Closest comparison

最接近的简单对照有两类：

1. **检索式 provenance：** 用 embedding / top-k relevance 选择看起来最相关的输入片段。
2. **生成式 provenance：** 直接让 LLM 标出或生成它认为支持答案的来源。

两者都可能得到短 provenance，但都不自动满足“把其余输入删掉后仍能复现原答案”的判据。BLIP 的增量不是更好的 citation ranking，而是增加一个可执行的 answer-preservation test。

## Decisive evidence

- 论文在 **7 个数据集**上评估，覆盖真实 QA / 文档任务与合成设置；作者报告 BLIP 生成的 provenance 满足答案复现约束，并在 provenance size 可比时，相比最佳 baseline 的 provenance accuracy 提升超过 **30%**。
- 推荐的 adaptive / pruning-search 组合把 provenance 压到原输入的一小部分，同时将总推理成本控制在与原始完整输入查询同一量级。这个结果说明“验证 provenance 必须指数级昂贵”并非必然。
- 论文还测试 multiple minimal provenances，提醒同一个答案可能有不止一条充分输入路径；因此 provenance 不应天然被解释为唯一因果解释。

这些结果最能支持的是 verification substrate：在不修改原模型和任务 pipeline 的情况下，事后构造一个可以重新执行的 answer witness。

## Cost and failure boundary

BLIP 是 bolt-on：它不要求重新训练模型，但会在原始 query 之后追加多轮 LLM 调用来搜索和验证候选子集。其成本优势依赖搜索策略能快速缩小候选空间；论文报告 adaptive strategy 的总成本与原始完整输入查询可比，但这仍是额外 verification budget，不应与“免费 citation”混在一起。

更关键的是 scope。当前定义针对**单次 LLM invocation**。真实 Data Agent 常有 retrieval → tool call → SQL/Python execution → intermediate state → review → retry 的多阶段轨迹。单次输入子集复现不能自动恢复工具状态、外部数据库版本、程序执行结果或跨步依赖，因此 workflow-level provenance 仍是开放问题。

## Skeptical audit

第一，BLIP 的 guarantee 是 answer preservation，而不是 truth preservation。如果完整输入上的原答案错误，那么能稳定复现这个错误答案的 provenance 仍然是错误的；它不能替代 Business Truth、ground-truth oracle 或 artifact correctness。

第二，“minimal”取决于模型与 query 的行为，而不等于人类意义上的完整因果解释。对于 negation、counting、average 等非单调/聚合问题，一个很小的子集可能偶然复现同一输出，却遗漏业务上必须审计的全集条件。

第三，输出是否“等价”本身可能需要 exact match 或 LLM judge。论文在低温条件下检查了输出稳定性，但在开放生成任务上，equivalence oracle 仍会影响 provenance 的可验证边界。

## Claim ceiling

现有证据支持：**LLM 数据处理的 provenance 可以从 relevance hint 提升为 executable answer-reproduction witness，而且在作者测试的 workload 上不必付出穷举式成本。** 这为 Data Agent 的 Verification & Recovery 提供了一个值得单独测量的中间层：`source relevance → answer-reproduction provenance → answer/business correctness`。

现有证据不支持：BLIP provenance 就是事实依据、因果解释或业务真相；也不支持它已经覆盖多工具、多步骤、带持久状态的 Agent workflow。

## Field-map consequence

该工作以 `early_signal` 进入 **Verification & Recovery**。它把已有的“provenance 与 correctness 分离”进一步操作化为可重放的 answer-preservation test，但只有一篇新工作，且作用域停留在单次 LLM invocation，因此不修改稳定 Field Map。
