# ReAct-SQL: separating grounding from composition with matched controls

[中文](2608.22651.md) | **English** · [Home](../README.en.md) · [Research Library](../library/README.en.md)

[Paper](https://arxiv.org/abs/2608.22651) · **Importance: 4/5**

> **Research delta.** The important result is not the headline that a simple ReAct loop beats elaborate pipelines. It is the three-stage incremental control under the same Gemini 2.5 Flash backbone, hints, and judge: one-shot raw SQL → raw-SQL ReAct → typed relational DSL. The marginal gains nearly reverse across EHR-SQL and BIRD, exposing different grounding and composition bottlenecks.

## Problem

Modern Text-to-SQL systems often add schema linking, retrieval, candidate generation, self-correction, and multi-stage orchestration together. A higher end score therefore does not reveal whether the gain came from actively inspecting data, from a structured query representation, or simply from more model calls. The useful decomposition is between finding the right tables, columns, and values and reliably composing a complex query after those choices are grounded.

## Mechanism

ReAct-SQL gives the model only the schema, question, and DSL documentation, then lets it build a query in a think → act → observe loop. The action space is not arbitrary SQL. It contains 15 typed relational operations: 12 Relation-building operations and 3 read-only probes. Relations are immutable and each operation creates a new handle; before compiling SQL, the engine validates tables, columns, and the currently visible fields, returning typed errors, result previews, and persistent handles to the next reasoning turn.

The three probes—`probe_values`, `value_exists`, and `sim_value_in`—let the model inspect stored values and formats. The DSL turns joins, filters, aggregation, projection, windows, and materialization into checked intermediate operations. The model decides when to stop under a 15-turn cap; mean usage is 3.3 turns on BIRD and 4.3 on EHR-SQL, with up to eight batched tool calls per turn.

## Closest comparison

The most causally useful comparison is not the ranking against CHESS, RSL-SQL, or DSR-SQL. It is the paper's own matched three-stage ablation:

1. **Baseline:** schema + question → one-shot raw SQL.
2. **+ Iteration:** keep raw SQL as the action, add only the ReAct execution-feedback loop.
3. **+ DSL:** replace raw-SQL actions with the typed relational DSL on top of iteration.

All three use Gemini 2.5 Flash, identical hints, and the same LLM judge, making this a much cleaner test of grounding control versus composition control than the cross-system table.

## Decisive evidence

- **EHR-SQL (n=934):** baseline 45.9% → raw-SQL ReAct 72.2%, a **+26.23-point** gain with 95% CI [+22.91,+29.66] and McNemar p≈10^-47. Adding the DSL reaches 73.9%, only **+1.71 points**, CI [-1.07,+4.50], p=.253.
- **Corrected BIRD mini-dev (n=498):** baseline 78.5% → iteration 79.1%, only **+0.60 points**, CI [-3.41,+4.62], p=.848. Adding the DSL reaches 84.5%, **+5.42 points** over iteration, CI [+1.61,+9.24], p=.006.
- This reversal matters more than the headline ranking. EHR is dominated by value/schema grounding uncertainty, while BIRD is comparatively easy to ground and more constrained by complex SQL composition. Whether agentic iteration is valuable therefore depends on the workload bottleneck.
- The cross-system result still has engineering value: ReAct-SQL reaches 84.5% / 73.9% on BIRD / EHR-SQL with median latency 7.5s / 13.2s. But RSL-SQL is cheaper on BIRD, so this is not a universal efficiency win.

## Cost and failure boundary

The loop is capped at 15 turns but averages only 3–4, and batched tool calls collapse multiple relation operations into one LLM round trip. Reported mean API cost is $0.0107/query on BIRD and $0.0166/query on EHR-SQL. Latency is strongly right-skewed and provider/network dependent: ReAct-SQL has a 7.5s BIRD median but one 1837.3s stall, so the speed claim is a median comparison in the measured environment, not a tail-latency guarantee.

The DSL also does not eliminate infrastructure; it moves complexity from prompt orchestration into a deterministic execution substrate: Relation IR, compile-time validation, SQL compilation, materialization, and answer shaping. That is a useful systems boundary, but not "zero infrastructure."

## Skeptical audit

Three alternative explanations matter most. First, the cross-system baselines are not fully matched: RSL-SQL uses a retriever over BIRD training pairs, CHESS lacks BIRD-style column descriptions on EHR, and DSR-SQL substitutes Gemini for its original backbone. The cross-system table therefore cannot establish that simple architecture is the independent cause of the gain.

Second, both benchmarks are scored by a fixed LLM judge rather than official strict execution-result equality. The judge is shared across systems, but the endpoint can still hide semantic discrepancies. Third, the EHR-SQL unanswerable subset is excluded, so the experiment does not test clarification, abstention, safe-to-answer, or business truth. It tests grounding and composition on answerable Text-to-SQL, not complete Data Agent correctness.

## Claim ceiling

The evidence supports a narrower and more useful claim: **for answerable Text-to-SQL, adaptive database probing and typed relational control are separable control layers, and their relative value depends on the workload bottleneck.** It also establishes a strong baseline principle: before adding elaborate multi-stage or multi-agent orchestration, compare against simple adaptive probing plus a deterministic typed substrate.

The evidence does not establish that iteration universally beats static schema linking, that a typed DSL is necessary for every database, that enterprise-scale schemas can drop schema pruning, or that SQL answer correctness equals business truth or artifact correctness.

## Field-map consequence

This work enters **Planning & Semantic Interaction** as an `early_signal` and connects to **Execution & Transformation**. It refines the direct-SQL-versus-intermediate-plan tension into **grounding probe policy × typed execution representation**, but one paper is not enough to change the stable Field Map.
