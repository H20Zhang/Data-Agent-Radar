# APEX-SQL：让 Schema Linking 变成 Hypothesis → Profiling → Verification

**中文** | [English](2602.16720.en.md) · [返回首页](../README.md) · [Research Library](../library/README.md)

[Paper](https://arxiv.org/abs/2602.16720) · **Importance: 4/5**

> **Research delta.** APEX-SQL 不把 schema linking 当成一次静态文本匹配，而是让 agent **主动查询真实 data distribution** 来验证 column、join 与 value 假设，再生成 SQL。

## Problem

Enterprise schema 里的 column name / description 往往不足以说明真实含义。相似字段可能存不同粒度、单位或编码；join key 表面合理却在数据里几乎不重合；用户提到的 value 可能根本不在猜测的 column 中。

只看 metadata 的 agent 容易在一开始就做错误 grounding，之后生成语法正确但语义错误的 query。

## Mechanism

`question → candidate schema hypothesis → profile/query real data → inspect values/distributions/overlap → revise hypothesis → generate/execute SQL`

这把 data access 从“最后执行 query”提前成 **grounding tool**。

## Closest comparison

最关键的 baseline 应是使用相同 base model、相同 schema metadata、相同 SQL execution backend，但不允许 active profiling 的静态 schema-linking agent。

如果探索组拥有更多 database calls/token budget，需要把这些额外成本计入。

## Decisive evidence

研究信号在于：真实 data 本身可以作为 schema semantics 的证据。对 ambiguous enterprise schema，这个信息源与 column name/document embedding 不同，能够验证或否定候选 grounding。

## What remains unproven

Active profiling 会增加 query latency、database load 与潜在 data exposure。大库/生产环境还可能限制 sampling、distinct-value lookup 或 unrestricted exploratory query。

因此下一步应做 cost- and permission-aware profiling：在相同 latency/query budget 下，哪些 probe 的 information gain 最高？什么时候 metadata 已经足够，不值得再访问 data？

## Field-map consequence

Data Discovery & Grounding 应显式区分：

`static metadata retrieval ↔ active evidence acquisition from the data itself`

这让 data agent 与一般 RAG 的边界更清楚：source 不是只读 document，而是可执行、可探测的 database environment。
